## P0 — Adoption blockers

### 1. Ingest is a single synchronous SSE stream with no job resource, no batch mode, and no async completion signal
*Integration & Consumability · severity high · effort M*

**Who hits it:** The onboarding team's overnight backfill of 250k legacy client files dies because their corporate API gateway kills idle-looking SSE connections at 60 seconds and their orchestrator has no job handle to resume or retry against.

**Recommendation (code-verified):** The finding's diagnosis is correct and understated: besides being SSE-only with no job resource, (a) the sync Azure Read polling in di/ocr/vision.py blocks the whole asyncio event loop (~60s/page — di_executor_workers exists in config but is never used), (b) the pipeline never emits status="error" — unhandled failures kill the stream silently after the 200 header, (c) client disconnect cancels the generator mid-way through non-transactional multi-connection writes, and (d) a disconnect between create_version and insert_knodes poisons retry: re-uploading the same bytes hits the content-hash noop check and skips forever, leaving the document permanently half-ingested. Fix in order: (1) decouple execution from the connection — POST /api/v1/ingest returns 202 + job_id from an ingest_job table (status, stage, terminal error, doc_id/version_id), pipeline runs in a background task, GET /api/v1/jobs/{id} for polling, keep SSE as optional GET /jobs/{id}/events; (2) add a top-level except in ingest_document that records a terminal failed job status (and emits a final error event on any live stream); (3) make ingest idempotent for retry — only mark a version 'current' after insert_knodes/merge complete (or gate the noop check on version completeness); (4) offload sync OCR via asyncio.to_thread/executor using the existing di_executor_workers setting; (5) then add POST /api/v1/ingest/batch fanning a manifest of object-store references out to jobs (config's s3_* settings are currently dangling and would need actual S3 client code), and either wire a worker for the arep_async=True 'deferred' reps into the same job machinery or default the flag to False — today deferred reps are never generated despite api-reference.md claiming they are queued.

**Evidence:** di/routers/ingest.py:15-29 (only ingest surface: POST→EventSourceResponse, no job/batch endpoints); di/pipeline.py:126 (sync vision.extract_pages inside async generator); di/ocr/vision.py:126-148 (sync httpx + time.sleep(0.5)×120 ≈ 60s poll; _pdf_ocr per page at vision.py:280-307); di/config.py:21 (di_executor_workers defined, zero run_in_executor/to_thread usages in di/); di/pipeline.py:124-223 (try/finally with no except — status="error" never emitted despite di/models.py:247 supporting it); di/pipeline.py:161 vs :193 + di/subtree/versioning.py:72-79 (create_version persists content hash before insert_knodes; retry of identical bytes → is_noop skip → permanent partial ingest); di/store.py:44-184 (per-stage connections, no cross-stage transaction); di/config.py:55 (arep_async=True default, no consumer anywhere) vs docs/technical/api-reference.md:125 (falsely documents a queue); di/config.py:62-66 (S3 settings unused); docs/specs/2026-06-24-document-intelligence-design.md and reports/requirements-and-interpretation.md D1-D13 (no async-ingest deferral recorded)

### 2. Document identity is the uploaded filename, with no idempotency key and a version-number race
*Integration & Consumability · severity high · effort M*

**Who hits it:** The branch scanning workflow uploads every document as 'scan001.pdf', so each new upload for a client silently supersedes an unrelated prior document instead of creating a new one.

**Recommendation (code-verified):** The core finding stands but the fix must be corrected for what the code actually does. (1) Accept an optional external_document_id form field on POST /api/v1/ingest as the logical document key (falling back to filename), and reject or explicitly flag uploads that would fall back to the router's literal "upload" default (di/routers/ingest.py:23), which currently collapses all unnamed uploads per client into one document. (2) Move content_hash + the no-op check before vision.extract_pages in di/pipeline.py so identical retries never re-pay Azure OCR. (3) Add a unique constraint on (client_id, doc_id, version_no) in di/migrations — note the existing doc_version_one_current partial index does NOT prevent duplicate version_no because create_version's UPDATE deactivates the competing current row first, and the soft-delete resurrection path (store.py:73 sets deleted_at=NULL on UPSERT while find_document filters deleted rows) produces duplicate version_no=1 even sequentially; fix that read/UPSERT asymmetry too. (4) The proposed "surface 409/skip on conflict" is insufficient on its own: the doc_version row is committed (pipeline.py:161) before knodes are inserted (pipeline.py:193), so a mid-ingest crash makes every identical-bytes retry a permanent no-op with zero knowledge nodes — either make version-flip + knode insert atomic (single transaction / mark version complete only after knodes land) or have the no-op check verify the current version actually has nodes. An Idempotency-Key header at the router is a reasonable addition but is secondary to (2)-(4), which make byte-identical retries safe by construction.

**Evidence:** di/pipeline.py:126-142 (OCR at 126 precedes content_hash at 129 and no-op check at 138; find_document(client_id, filename) at 130); di/routers/ingest.py:23 (filename defaults to literal "upload"); di/store.py:66-73 (UPSERT ON CONFLICT (client_id, document_name), DO UPDATE sets deleted_at=NULL resurrecting soft-deleted docs) vs store.py:47 (find_document filters deleted_at IS NULL); di/store.py:100-115 (create_version: read-then-write across transactions; UPDATE deactivates competitor's current row then inserts duplicate version_no); di/migrations/002_core_tables.sql:28,46-48 (UNIQUE(client_id,document_name); only partial unique on (client_id,doc_id) WHERE is_current — nothing on version_no); pipeline.py:161 vs 193 (version row committed before knodes — crash between makes retries permanent no-ops); reports/requirements-and-interpretation.md D1-D13 and Q-A..Q-N contain no decision on document identity or idempotency; docs/architecture/flows/merge-versioning-flow.md:151 codifies filename-as-identity without collision reasoning and inaccurately claims the hash runs "before any expensive work".

### 4. PII masking is caller-opt-in with no server-side policy, and /documents returns raw OCR text with no mask at all
*Security, Compliance & Governance · severity high · effort M*

**Who hits it:** The periodic-review team builds a review screen against /documents and /facts with defaults, and full SSNs and CURP strings end up rendered in the UI and captured in their web-tier access logs.

(3) For redacted raw-text serving, the PII spans are already persisted with start/end offsets in di_decision_trace.pii_entities — apply span redaction to ocr_text (and map offsets into ocr_lines) rather than re-detecting at serve time.

### 5. No eventing or webhooks for downstream change propagation — only per-client timestamp polling via GET /changes
*Integration & Consumability · severity high · effort M*

**Who hits it:** The periodic-review scheduler needs to re-score any client whose merged facts changed this week, and its only option is issuing millions of per-client /changes polls on a timer.

**Recommendation (code-verified):** Phase 1 (core, do before production rollout): add a monotonic change cursor and a cross-client feed. Concretely: (a) add an unpartitioned, non-RLS change-outbox table (or a bigserial `seq` on doc_version plus an RLS-exempt reader path — note doc_version is FORCE RLS per 004_rls.sql, so a separate summary table with client_id/doc_id/version_no/event_type/seq is cleaner than punching an RLS hole) written in the same transaction as version-created and facts-merged (the current feed misses client_merged_fact changes entirely); (b) expose GET /api/v1/changes?cursor=...&limit=... returning rows ordered by seq with an opaque next_cursor; (c) replace the raw `since` string on the per-client endpoint with a validated parameter (currently an invalid value 500s via the asyncpg ::timestamptz cast) and document that timestamp polling can permanently miss late-committing rows (created_at is transaction-time now(); the >= comparison already re-delivers equal timestamps, so the failure mode is commit-visibility skew, not equal-timestamp misses as originally stated). Phase 2 (when a real push consumer exists): drain the same outbox to the bank's event bus or a webhook-subscription API (HMAC-signed, retry with backoff) — defer this until a consumer demands push; the cursor feed alone makes millions-of-clients change detection O(changes) instead of O(clients).

**Evidence:** di/routers/clients.py:34-37 (client-scoped /changes, raw `since: str | None`); di/store.py:290-303 (`v.created_at >= $n::timestamptz`, per-client RLS acquire — note `>=`, so equal timestamps duplicate rather than miss); di/migrations/002_core_tables.sql:34-48 (doc_version: created_at DEFAULT now(), no monotonic sequence column); di/migrations/004_rls.sql (FORCE RLS on doc_version — cross-client feed structurally blocked); docs/brd/business-requirements.md:80 (G7 millions of clients), :122-133 (§5.2 out-of-scope list omits eventing — never deferred, and no decision D1-D13 covers it); reports/requirements-and-interpretation.md:246 (delta feed is explicitly 'for periodic re-KYC [v1]'); docs/specs/2026-06-24-document-intelligence-design.md:194 (polling feed is the designed change surface); grep of di/, docs/, reports/ finds no webhook/queue/pub-sub — only per-request SSE ingest progress (di/routers/ingest.py), which is not change propagation. Feed also omits client_merged_fact changes entirely (di/store.py:294-296 selects doc_version only).

### 7. Ingestion is a request-scoped synchronous pipeline with no durable queue, backpressure, or resumability
*Scale, Reliability & NFRs · severity high · effort L*

**Who hits it:** The periodic-review batch team kicks off the quarterly re-ingest of 2M client files and must hold 2M long-lived HTTP connections, with every LB timeout or pod restart silently losing a document.

**Recommendation (code-verified):** Split the write path into accept-and-enqueue: POST /api/v1/ingest returns 202 + job_id after persisting the raw file to object storage (wire up the existing but unused S3 settings in di/config.py:62-66 and the always-NULL s3_uri column) and enqueuing to a durable queue consumed by horizontally scalable workers; expose GET /api/v1/jobs/{id} with optional SSE re-attach, and enforce per-tenant rate/concurrency limits at enqueue time. Two corrections to the original recommendation: (1) do NOT key retry idempotency on the content hash alone — the existing same-hash noop check (di/subtree/versioning.py:72-73) already poisons retries: a crash between create_version and insert_knodes leaves a current version with zero knodes that a re-upload treats as 'identical content already current' and skips forever; checkpointing needs a per-version completion marker (or a transaction spanning create_version→insert_knodes) so same-hash-but-incomplete resumes instead of no-ops. (2) The worker tier also supplies the missing execution substrate for the already-decided-but-unimplemented arep async backfill (arep_async=True today means areps are silently never generated), and fixes the event-loop-blocking sync OCR call (di/pipeline.py:126) that currently serializes all requests behind one scanned-PDF OCR. Interim hardening regardless: an upload size limit and moving extract_pages off the event loop via the configured-but-unused executor.

### 11. No retention, right-to-erasure, or tenant off-boarding capability — data only ever accumulates
